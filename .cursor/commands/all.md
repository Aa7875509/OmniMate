# 真人级 3D AI 数字人直播软件 PRD 2.0

根据你确定的三个核心决策，项目正式采用以下路线：

- 运行方式： 本地实时渲染，数字人画面在用户自己的电脑上生成。
- 数字人来源： 使用现成 MetaHuman 作为基础，后续定制面部、发型、服装和角色风格。
- 动作方式： 完全由 AI 自主驱动，不依赖摄像头捕捉真人表情或动作。
- 开发技术： Electron + Vue 3 + TypeScript + Node.js，配合 Unreal Engine 5。
- 直播目标： 数字人可以自主说话、思考、表现情绪、做手势，并实时回应抖音弹幕。

这意味着我们要开发的不是传统的 3D 角色播放器，而是一套由 AI 驱动的实时数字人表演系统。

### 架构中的关键决策

1\. Unreal Engine 负责画面，不负责全部业务。 AI、弹幕、队列和角色配置由 Node.js 管理，避免业务逻辑与 3D 蓝图耦合。

2\. 数字人自主驱动，不等于让 LLM 直接控制骨骼。 AI 只输出受约束的表演计划，真正的动作由 Unreal 中的动画控制器执行。

3\. 本地渲染与云端 AI 分离。 第一版可以使用云端 LLM 和 TTS，但数字人渲染必须在本地完成。这样能降低本地 AI 推理负担，同时保持 3D 画面实时性。

4\. 直播推流不自研。 通过 OBS 完成场景合成和推流，减少编码器、音视频同步和平台适配的开发工作。

## 二、核心技术选型与实施边界

Epic 的官方文档说明，MetaHuman Animator 支持从音频、视频等输入生成面部动画；实时音频驱动也有对应工作流。

因此，建议采用以下实现组合：

| 能力    | 最终方案                                   | 关键说明                |
| ----- | -------------------------------------- | ------------------- |
| 真人级人物 | MetaHuman + UE5                        | 使用现成角色，后续再做外观定制     |
| 实时渲染  | Unreal Engine 5                        | 在本地 GPU 上渲染         |
| AI 对话 | Node.js + LLM Provider                 | 管理人设、上下文、回复策略       |
| 语音生成  | TTS Provider                           | 输出音频，优先支持流式播放       |
| 口型与面部 | MetaHuman Animator 音频驱动工作流或兼容的音频驱动面部系统 | 需要验证与实际 TTS 输出的实时集成 |
| 全身动作  | UE5 动画蓝图、Control Rig、动作资源库             | 由 AI 选择动作，不依赖真人动作捕捉 |
| 情绪表达  | AI 情绪标签 + 面部表情控制                       | 表情强度、持续时间和过渡由引擎控制   |
| 直播事件  | Node.js 直播平台适配器                        | 先模拟，再对接有权限的抖音接口     |
| 视频输出  | UE5 + OBS                              | 优先验证窗口采集，再优化透明背景输出  |

这里有两项不能跳过的技术验证：

1. TTS 音频能否在你的目标 UE5 版本中驱动实时面部动画。 官方支持音频驱动动画，并不自动意味着任意 TTS 流都能直接接入；需要验证音频输入方式、缓冲、时间戳和动画延迟。
2. AI 全身动作不能只靠音频生成。 招手、转身、摊手、比心等动作需要可调用的动画资源或程序化控制，再由 AI 根据对话选择动作。

官方 MetaHuman 页面目前列有音频驱动和其他面部动画能力，项目应以最终锁定的 UE5 版本及插件实际支持情况作为实施依据。

## 三、产品功能模块与边界

建议将整个系统划分为 8 个模块，分别开发、测试和验收。

M1：数字人引擎

负责人：UE5 模块

- 加载 MetaHuman、初始化场景与灯光
- 待机动画、视线、眨眼和头部微动作
- 表情、口型、身体动作的统一调度
- 帧率、GPU 使用率和资源状态监控

M2：AI 大脑

负责人：Node.js

- 角色人设、记忆和直播主题
- 对话上下文与回复生成
- 情绪判断、动作规划
- 内容安全和回复长度控制

M3：语音与口型

负责人：语音服务与 UE5

- TTS 合成、音频播放和中断
- 口型数据同步
- 音频开始、结束和失败事件
- 语音与表演状态同步

M4：直播互动

负责人：Node.js

- 弹幕接入、去重、过滤、队列
- 礼物和点赞事件规则
- 用户昵称播报
- 断线重连与事件日志

M5：桌面控制台

负责人：Electron + Vue 3

- 角色选择、AI 人设配置
- 实时预览、弹幕面板、日志
- 直播开始、暂停、恢复、停止
- 手动输入和人工接管

M6：动作编排器

负责人：Node.js + UE5

- 动作白名单与优先级
- 动作衔接、打断、冷却时间
- 表情强度和动作持续时间
- 失败回退与动作冲突检测

M7：直播输出

负责人：UE5 + OBS

- 渲染窗口输出
- 音频设备与混音
- OBS 场景配置
- 直播预演与正式输出切换

M8：稳定性与安全

贯穿所有模块

- 密钥保护、输入过滤和操作审计
- 超时、重试、取消和恢复
- 资源泄漏检测
- 自动回复限流和紧急停止

### MVP 的明确范围

第一版必须完成 M1、M2、M3、M5、M6、M7 的最小实现，以及 M4 的模拟弹幕模式。

正式抖音接入可以并行验证，但不能成为整个开发的前置条件。M8 的基础安全和停止能力必须随首个可运行版本一起交付，而不是留到最后。

## 四、数字人自主表演系统设计

这是整个产品最重要的差异化能力。

目标不是让 AI 每次只决定一个动作，而是让数字人形成一套连续、自然的表演：听到问题时表现思考，回答时自然注视镜头，讲到重点时配合手势，结束后回到待机状态。

### 4.1 AI 表演计划

建议把一次回答拆成三个层次：

- 语义层： AI 决定说什么。
- 表演层： AI 决定用什么情绪、手势和头部姿态。
- 执行层： Unreal Engine 根据动作资源和动画状态机实际执行。

例如，观众发送“你今天怎么这么开心？”时，AI 可以生成以下计划：

```
export type Emotion =
  | 'neutral'
  | 'happy'
  | 'sad'
  | 'surprised'
  | 'confused'
  | 'thinking'

export type Gesture =
  | 'none'
  | 'wave'
  | 'nod'
  | 'open_palm'
  | 'hand_on_chest'
  | 'heart'
  | 'shrug'

export interface PerformancePlan {
  replyId: string
  text: string

  emotion: {
    type: Emotion
    intensity: number // 0~1
  }

  gesture: {
    type: Gesture
    startOffsetMs: number
    durationMs: number
  }

  gaze: 'camera' | 'slightly_left' | 'slightly_right'

  speechStyle: {
    rate: number
    emphasis: 'normal' | 'gentle' | 'strong'
  }
}
```

这份数据只是业务意图，不能直接控制 Unreal 中的任意骨骼。执行层必须检查动作是否存在、强度是否在有效范围内，以及当前动作是否允许被打断。

建议采用以下动作映射：

| AI 意图 | 面部表现        | 身体动作      |
| ----- | ----------- | --------- |
| 思考    | 轻微眯眼、短暂转移视线 | 轻微歪头、短暂停顿 |
| 开心    | 微笑、自然眨眼     | 点头、适度摊手   |
| 感谢    | 温和微笑、眼神注视镜头 | 手放胸前、轻微鞠躬 |
| 疑惑    | 眉毛变化、轻微眯眼   | 歪头、摊手     |
| 惊讶    | 眼睛睁大、眉毛上扬   | 短暂后仰或抬手   |
| 解释重点  | 保持稳定眼神      | 配合一次开放手势  |
| 倾听    | 中性表情、轻微眨眼   | 自然呼吸、轻微点头 |

真实感不等于每句话都要做动作。建议把大部分普通回答设计成低强度微动作，只有在语义确实需要时才触发明显手势。

### 4.2 动作系统采用混合驱动

不建议用一个 AI 模型实时生成所有骨骼数据。首版采用“预制动作 + 程序化微动作 + AI 选择”的方式。

预制动作库

招手、点头、摊手、感谢、比心、轻微转身等动作。提供经过调试的动画片段，保证基本姿势和动作质量。

程序化微动作

呼吸、轻微头部摆动、视线变化和自然眨眼。通过受限的曲线、随机间隔和过渡规则控制，避免机械重复。

AI 表演决策

选择情绪、动作、注视方向和强调程度；由动画控制器决定具体执行时机与冲突处理。

### 4.3 UE5 动画状态机

建议建立以下状态：

`Idle → Listening → Thinking → Speaking → Recovery → Idle`

其中：

- `Idle`：呼吸、眨眼、视线微调。
- `Listening`：面部注意力状态，不需要真人输入动作。
- `Thinking`：短暂停顿、思考表情。
- `Speaking`：口型驱动与身体手势并行。
- `Recovery`：平滑收回手势、恢复自然姿态。
- `Interrupted`：人工接管或紧急停止后的清理状态。

口型和身体动画需要分层。UE5 可以使用动画蓝图、Control Rig 和 MetaHuman 面部控制系统组合执行；官方文档提供这些动画工作流。

## 五、模块通信接口设计

建议 Electron、Node.js 与 Unreal Engine 之间使用明确的通信协议，而不是让 Vue 直接操作 UE5 内部对象。

### 5.1 通信方式

| 通信路径               | 推荐方式                 | 用途                |
| ------------------ | -------------------- | ----------------- |
| Vue → Electron     | 安全 IPC               | 本地设置、窗口管理、应用操作    |
| Electron → Node.js | 本地 WebSocket 或受控 IPC | 对话、直播事件、业务状态      |
| Node.js → Unreal   | 本地 WebSocket         | 表演计划、音频控制、动作指令    |
| Unreal → Node.js   | WebSocket 事件         | 动作开始、动作完成、渲染状态、错误 |
| Node.js → AI/TTS   | HTTPS / 服务端 SDK      | 对话生成与语音合成         |
| 抖音服务 → Node.js     | 官方授权的服务端推送或接口        | 弹幕和直播事件           |

建议把 Node.js 作为唯一的业务编排入口，Unreal Engine 只接受经过校验的表演指令。

### 5.2 统一消息协议

```
export interface RuntimeMessage<T = unknown> {
  protocolVersion: '1.0'
  messageId: string
  sessionId: string
  timestamp: number
  type: string
  payload: T
}
```

每条消息应包含唯一 ID、会话 ID、协议版本和时间戳。客户端收到重复命令时应能去重，收到旧会话的消息时应拒绝执行。

### 5.3 Node.js → UE5 的命令示例

```
export interface SpeakCommand {
  replyId: string
  text: string
  audioUrl?: string
  emotion: Emotion
  gesture: Gesture
  priority: number
  expiresAt: number
}

export interface StopCommand {
  reason: 'manual' | 'interrupted' | 'emergency'
  replyId?: string
}
```

实际项目中，若 TTS 音频保存在本地，建议使用受控文件路径或二进制音频通道，不要把大段 Base64 音频直接放进普通 JSON 消息。

还要注意：`audioUrl` 如果来自云端服务，UE5 本地运行进程必须有正确的访问权限和音频解码能力。首版可以先使用本地临时音频文件验证端到端流程，再升级为流式音频。

### 5.4 UE5 → Node.js 的事件示例

```
export interface AvatarRuntimeEvent {
  type:
    | 'engine.ready'
    | 'avatar.ready'
    | 'speech.started'
    | 'speech.finished'
    | 'action.started'
    | 'action.finished'
    | 'render.stats'
    | 'engine.error'

  sessionId: string
  taskId?: string
  timestamp: number

  payload?: Record<string, unknown>
}
```

Node.js 通过这些事件判断数字人是否已经准备好、是否正在说话，以及当前任务是否可以结束。不能仅根据 TTS 服务返回成功就认为数字人已经完成表演。

### 5.5 取消与超时机制

每个对话任务需要有独立的 `taskId` 和 `AbortController`。

当用户按下紧急停止时：

1. Node.js 立即取消可取消的 AI 和 TTS 请求。
2. 清空尚未执行的普通互动队列。
3. 向 UE5 发送停止命令。
4. UE5 停止音频、退出可中断动作并恢复安全状态。
5. 忽略之后到达的旧任务结果，直到用户明确恢复。

如果第三方服务不支持真正取消请求，系统也必须通过任务 ID 阻止旧结果再次播出。

## 六、性能指标与硬件配置

真人级渲染的性能目标不能只看 GPU 型号。MetaHuman 模型复杂度、头发、灯光、阴影、渲染分辨率和面部动画都会影响最终帧率。

Epic 官方给出的部分 MetaHuman 编辑和动画功能推荐配置包括 32GB 内存、至少 8GB 显存，以及 RTX 3070、RX 6800 XT 或 Apple M2 Ultra 级别的 GPU。需要注意，这是特定创作功能的推荐要求，并非完整直播软件的性能保证。

### 6.1 建议的目标运行配置

基础开发与测试机

建议 32GB 内存、8GB 以上显存的独立 GPU，使用 SSD。适合单个数字人、中等质量灯光与 1080p 输出的初步验证。

推荐直播运行机

建议 64GB 内存、12GB 以上显存的较新独立 GPU。目标是在 UE5、OBS 和其他桌面程序同时运行时保留性能余量。

以上是项目选型建议，不是厂商保证的最低规格。Mac 与 Windows 的插件、渲染后端和音频驱动能力存在差异，正式开发应先锁定目标操作系统。

### 6.2 性能验收指标

以下指标作为首轮工程验收目标，需要在指定测试机上实测后再定版。

| 指标      | MVP 目标                                   |
| ------- | ---------------------------------------- |
| 实时渲染    | 1080p 输出，目标 30 FPS，稳定场景优先                |
| 帧时间     | 30 FPS 对应单帧约 33.3ms；需要监控持续帧时间而非只看平均值     |
| AI 首段文本 | 普通网络环境下目标 P95 不超过 3 秒                    |
| 首次语音播放  | 从有效消息进入队列到开口，目标 P95 不超过 5 秒              |
| 口型同步    | 音频和口型连续，不出现明显冻结或长期偏移                     |
| 动作响应    | 动作指令被 UE5 接收后，目标在 200ms 内开始可见响应，复杂过渡单独评估 |
| 持续运行    | 2 小时压力测试无崩溃、无持续性内存增长                     |
| 恢复能力    | AI 或弹幕断线时，数字人仍可手动控制                      |
| 队列治理    | 可配置队列长度、过期时间、优先级和重复消息处理                  |

其中 AI 和语音延迟受网络、模型、服务商和排队时间影响，不能保证所有请求都达到固定时限。应分别记录 AI 生成延迟、TTS 延迟、UE5 指令延迟和实际开口延迟，定位瓶颈。

### 6.3 直播输出方案

第一版建议先采用 UE5 独立渲染窗口 + OBS 窗口采集，不一开始就追求复杂的透明背景视频流。

实施顺序：

1. UE5 输出固定背景画面与声音。
2. OBS 正常采集并推流，验证画面和音频稳定性。
3. 增加独立背景、绿幕或透明背景需求。
4. 根据实际采集方式验证 Alpha 通道、边缘质量和音画同步。

Unreal Engine 官方支持项目 Alpha 输出相关设置，但透明背景的实际可用性取决于渲染配置与采集链路，不能认为开启 Alpha 后所有 OBS 采集方式都自动支持透明合成。

## 七、开发计划：建议按 8～10 周实施

对于你一个前端工程师主导的项目，我建议先建立可运行的技术验证版本，再开发完整产品。最大的风险不在 Vue 页面，而在 UE5 数字人实时驱动、音频同步和长时间运行。

## 第 1 周

阶段 A：UE5 技术验证

- 安装并锁定 Unreal Engine 版本。
- 获取一个可用 MetaHuman 并在本地运行。
- 验证渲染、骨骼动画、面部表情和基础待机动作。
- 输出一个稳定运行的独立程序。

验收：无需编辑器操作即可运行数字人演示。

## 第 2 周

阶段 B：自主动作系统

- 实现待机、招手、点头、摊手等动作。
- 建立动画状态机与动作优先级。
- 实现表情、视线和基础微动作。
- 验证动作之间的过渡和中断。

验收：通过测试指令控制数字人完成一组连续动作。

## 第 3 周

阶段 C：语音驱动

- 接入 TTS。
- 验证 TTS 音频进入 UE5 的实时口型驱动方案。
- 实现音频开始、播放中、结束和取消事件。
- 测量首段语音延迟和口型同步情况。

验收：数字人能够连续朗读文本，并表现出与语音匹配的面部运动。

## 第 4 周

阶段 D：AI 大脑

- 接入 LLM 和角色人设。
- 生成结构化表演计划。
- 建立动作白名单、内容过滤和任务超时。
- 完成 Node.js 与 UE5 的双向通信。

## 十、现在最应该做什么

我建议暂时不要继续扩展功能清单，先做一个独立的技术验证项目，重点攻克三个问题：

1. MetaHuman 本地实时渲染是否达到目标画质和帧率。
2. AI 生成的 TTS 音频能否驱动自然、连续的面部动画。
3. AI 表演计划能否稳定驱动身体动作，同时避免动作冲突和音画不同步。

其中第二项是最关键的技术风险。MetaHuman 官方文档区分了实时音频输入和离线音频驱动动画；如果目标是直播时对任意新生成的 TTS 音频即时做出面部表演，就必须先验证真正的实时链路，不能拿离线处理成功作为实时可用的证明。
